# NTable 实用功能迭代调研

调研日期：2026-10-04。本文只提出方案，未实施功能。以当前工作区源码、公共契约和 `app/AGENTS.md` 为依据；不把旧架构设想或演示能力当成组件已交付能力。主会话验证：`npm run verify` 通过（27/27 测试），`npm pack --dry-run --cache /tmp/ntable-npm-feature-cache` 通过（22 个文件、29.4 kB，无 demo/worker）。复用内置浏览器观察本地页面：10040 条记录，视图菜单仅删除，无匹配搜索显示 0 条。此为轻量交互观察，不是完整浏览器回归或真实后端验收。

## 判断与优先级

NTable 已经具有本地树形数据投影、筛选 AND/OR、空值判断、多级排序、冻结列、列拖拽与缩放、虚拟行、保存视图和记录打开。下一步应补足“真实业务接入后的可用性”，不扩成通用多维表格平台。

| 顺序 | 建议 | 用户收益 | 相对成本 | 边界 |
| --- | --- | --- | --- | --- |
| 1 | 类型驱动筛选与显示标签搜索 | 能准确找出日期区间、多选标签和中文选项 | 中 | 日期/多选新语义需先修订产品规则和契约 |
| 2 | 受控行选择，交给宿主执行批量工作流 | 勾选结果真正可供业务使用 | 小到中 | 不把批量审批、删除或导出塞进核心表格 |
| 3 | 数据加载、失败与重试状态 | 用户能区分无数据、无结果和网络故障 | 小到中 | 网络请求和重试实现仍归宿主 |
| 4 | 视图重命名与显式复制 | 视图可长期维护和复用 | 小到中 | 演示的新建已复制当前配置，新增应补任意视图复制协议 |
| 5 | 只读能力控制 | 同一组件用于管理和查看场景 | 中 | 组件只表达能力，服务端执行权限校验 |
| 6 | 完整键盘浏览与树形焦点管理 | 高频录入核查、无鼠标操作更高效 | 中到大 | 只增强浏览、选择、打开，不加行内编辑 |
| 7 | 可选远程查询模式 | 支持无法全量下载的数据集 | 大 | 真实数据规模证明必要后再做 |

成本为基于改动范围的相对判断，不是工期承诺。前三项可分批交付：先把受控选择和数据状态接入一个真实宿主，再扩充筛选语义。远程查询不应仅因为存在行虚拟化就启动。

## 1. 类型驱动筛选与显示标签搜索

**场景。** 运营查某日期区间的记录；设计按多选标签查“包含任一指定标签”；用户输入界面看到的中文状态名称搜索。

**当前证据。** [types.ts:6](../app/src/ntable/types.ts#L6) 已有日期、单选、多选；但 [FilterPanel.tsx:23](../app/src/ntable/FilterPanel.tsx#L23) 对所有需要值的条件统一使用文本输入框。[filtering.ts:29](../app/src/ntable/filtering.ts#L29) 只区分数字与非数字，[filtering.ts:38](../app/src/ntable/filtering.ts#L38) 将数组转字符串比较；[tree.ts:20](../app/src/ntable/tree.ts#L20) 搜索原始值。因此 `status="ready"` 即使显示“已就绪”，搜索“已就绪”也不能由现有逻辑命中该字段。限制已明确记在 [business-api-contract.md:144](./business-api-contract.md#L144)。现有 AND/OR 和空值条件已经实现，不应再作为新功能推荐。

**MVP。** 单选从 schema.options 选择，界面显示 label、持久化 value；搜索匹配可见字段的显示文本。第二步增加多选“含任一/含全部/不含”集合语义和日期“早于/晚于/区间”日历输入。先只支持绝对日期区间，不同时加入“本周”等时区与时钟依赖。

**收益与成本。** 用户不用猜内部枚举值，筛选从字符串技巧变成业务语义。成本主要在 FilterRule 的兼容演进、已有视图迁移、输入控件和树形查询回归。

**边界。** [app/AGENTS.md:46](../app/AGENTS.md#L46) 明确规定当前非数字运算符；日期和集合操作必须先更新这一规则，不可直接替换已有 contains 行为。宿主负责 schema 与存量视图迁移；组件负责输入、序列化和本地判断一致性。UI 样式仍须按项目的飞书参照验收。

**验收。** 中文 label 搜索命中对应 value；隐藏与 searchable=false 字段仍不参与搜索；`["a","ab"]` 的集合选择不会因子串误命中；区间首尾日期、空值和非法日期有明确行为；旧视图可读取且原有语义不静默变化；筛选命中子记录继续保留祖先。

方向参考：Airtable 官方说明日期上下界可以组成范围条件，筛选运算符按字段语义使用。这是需求方向的佐证，不是 NTable 的 UI 替代参考。[Filtering records using conditions](https://support.airtable.com/articles/9290731839-filtering-records-using-conditions)

## 2. 受控行选择，连接宿主批量工作流

**场景。** 业务需要拿到勾选记录，用于批量分配、导出所选、核对清单或审批。

**当前证据。** [Table.tsx:34](../app/src/ntable/Table.tsx#L34) 将 selected 保存在内部 Set；[types.ts:33](../app/src/ntable/types.ts#L33) 没有选择输入和变化回调。全选只作用于投影后可见行，见 [tree.ts:75](../app/src/ntable/tree.ts#L75)；切换视图会清空选择，见 [Table.tsx:104](../app/src/ntable/Table.tsx#L104)。当前勾选能显示计数，但标准 NTable 接入的宿主无法消费结果。

**MVP。** 提供可选 selectedRowIds/onSelectionChange，保留当前非受控默认；把选中 ID 交给宿主自己的操作区。明确切换视图清空、筛选暂时隐藏仍保留、数据移除时剔除失效 ID 等规则；给宿主提供主动清空选择能力。选中父记录与子记录仍各自独立，不默认级联。

**收益与成本。** 少量公共契约增量即可让现有选择能力参与业务流程。成本主要是受控/非受控同步与树形、筛选、视图切换边界。

**边界。** 核心表格只扩展“行选择”能力；批量写入、操作权限、失败项处理、导出格式由宿主负责。[app/AGENTS.md:30](../app/AGENTS.md#L30) 限定 footer 只有计数，因此不在 footer 加批量操作入口。若未来想在 NTable 工具栏内放批量动作，要另行调整范围规则。

**验收。** 勾选一次只发出一次准确变更；外部清空立即反映；排序不改选中 ID；隐藏结果和折叠子树不会造成“已选择计数”和宿主 ID 不一致；全选不会悄悄包含未显示的子记录；宿主操作失败不会由表格擅自改记录或重试。

## 3. 数据加载、失败与重试状态

**场景。** 用户第一次打开真实业务列表、刷新数据失败、筛选无结果，需要知道当前发生什么。

**当前证据。** [Table.tsx:326](../app/src/ntable/Table.tsx#L326) 对所有零行场景显示“没有符合条件的记录”；紧接的 loading 来自 [Table.tsx:49](../app/src/ntable/Table.tsx#L49) 的 useDeferredValue，只表示视图投影延后。公共契约 [types.ts:33](../app/src/ntable/types.ts#L33) 没有外部数据加载/错误状态；请求与持久化明确属于宿主，见 [component-integration.md:5](./component-integration.md#L5)。不能把已有视图加载提示当作远程请求状态支持。

**MVP。** 添加可选的外部数据状态与 retry 回调；区分初次加载、后台刷新、请求失败、原始数据为空、当前条件无结果。后台刷新保留旧数据和滚动位置；表头、工具栏保持稳定。无结果时提供清空搜索/筛选入口，但没有记录时不出现误导文案。

**收益与成本。** 用户不用用空白推断网络故障；宿主不必把整个表格卸载后显示 spinner。状态契约和空态改造成本较低，异步状态优先级需要明确。

**边界。** 请求、取消、重试节流和错误细节由宿主处理；组件仅展示受控状态和发出操作意图。视图保存成功/失败属于另一条状态线，不能与数据加载混用；乐观保存和冲突恢复继续由宿主承担，见 [business-api-contract.md:174](./business-api-contract.md#L174)。

**验收。** 首次加载不闪现无结果；失败可重试且只触发宿主一次；后台刷新不清空选择/滚动；无查询空表与有查询无结果文案不同；状态有可访问播报；不新增尾行添加入口。

## 4. 视图重命名与显式复制

**场景。** “临时视图”成为长期工作视图后要改名；用户希望从指定部门视图复制配置，再做少量调整。

**当前证据。** [ViewBar.tsx:9](../app/src/ntable/ViewBar.tsx#L9) 有新建；[ViewBar.tsx:16](../app/src/ntable/ViewBar.tsx#L16) 当前菜单只有删除。[App.tsx:116](../app/src/App.tsx#L116) 演示新建已从 activeView 复制配置，不能把“复制当前视图”误报成完全缺失。创建回调只有 name，初始化方式由宿主决定。

**MVP。** 先支持重命名；如业务确需复制任意视图，再补显式复制入口和源视图 ID 回调，由宿主创建新 ID 并独立保存配置。不要仅把演示已经存在的复制改名成新特性。

**收益与成本。** 视图可持续维护；指定源视图复制减少重复配置。重命名成本小，显式复制还需确定个人筛选是否带入和宿主的持久化协议。

**边界。** 仍是已允许的保存视图能力。名称校验、ID 与持久化归宿主，组件负责交互和乐观反馈。是否允许删除、创建由下一项能力控制决定。

**验收。** 重命名不改 id 或其他配置；空名处理一致；复制后的修改不影响原视图；复制携带的列宽、冻结、字段和查询范围与协议一致；失败不会丢失源视图，且不回滚期间发生的新操作。

## 5. 只读能力控制

**场景。** 外部查看页面允许搜索和个人筛选，但不能改共享布局、创建或删除视图。

**当前证据。** [types.ts:38](../app/src/ntable/types.ts#L38) 创建/更新是必需回调，没有对应只读能力；不传 onAddRecord/onDeleteView 只能隐藏这两个入口。[TableToolbar.tsx:11](../app/src/ntable/TableToolbar.tsx#L11) 字段配置、筛选、排序入口默认都展示。

**MVP。** 用独立 capabilities 表达创建、重命名、删除与布局调整能否使用；不在组件内建立角色系统。统一收口菜单、表头拖拽、冻结、缩放、字段面板的行为。

**收益与成本。** 同一组件可用于管理页和查看页；成本中等，主要来自分散写入入口的一致限制。

**边界。** 当前规则提示筛选只对个人生效，见 [business-api-contract.md:219](./business-api-contract.md#L219)；只读共享布局不应顺手禁掉个人筛选。宿主决定权限并在后端验证，隐藏按钮不是授权。新的 capabilities 与持久化归属需先写入文档。

**验收。** 只读状态没有可触发写入的隐藏入口；能力动态变化能立即生效并取消尚未提交的禁止操作；查看者仍可搜索和按许可做个人筛选；数据权限由真实宿主后端验收。

## 6. 完整键盘浏览与树形焦点管理

**场景。** 用户逐行核查长列表，使用键盘打开记录、返回继续浏览，或使用读屏器识别父子关系。

**当前证据。** [Table.tsx:324](../app/src/ntable/Table.tsx#L324) 声明 role=grid；[Table.tsx:325](../app/src/ntable/Table.tsx#L325) 每行 tabIndex=0 并支持 Enter 打开，这部分已存在；没有完整的方向键网格导航。[Table.tsx:481](../app/src/ntable/Table.tsx#L481) 有层级展开按钮。不能把“键盘打开记录”作为全新功能，也不能仅凭源码认定读屏器实测结果。

**MVP。** 确定普通表格和层级 treegrid 的语义；建立单一 Tab 入口与活动行/单元格，支持方向键、Home/End、PageUp/PageDown、选择快捷键、树节点展开折叠。打开详情后返回原记录；虚拟化移出 DOM 时保留逻辑焦点并滚动到位。列重排和缩放提供无鼠标替代入口。

**收益与成本。** 减少长表格 Tab 跳转，提高浏览效率与可访问性。成本较高，原因是虚拟化、冻结列、树形展开和弹层焦点需要一起协调。

**边界。** 保持只读单元格和现有打开记录方式；快捷键在输入框、浮层中不得劫持文本编辑。现有飞书样式与密度不变。

**验收。** 仅用键盘可浏览、勾选、展开、打开与返回；跨虚拟页不丢焦点；折叠当前焦点所在子树时回到父行；筛选移除焦点行有确定回退；读屏能读出层级、展开与选中状态；使用真实浏览器/读屏器验收，而非只检查 ARIA 属性。

规范依据：W3C APG grid 说明复合网格一般只保留一个 Tab 入口并由组件管理内部方向导航；treegrid 提供树形表格的键盘和语义模式。[Grid pattern](https://www.w3.org/WAI/ARIA/apg/patterns/grid/)、[Treegrid pattern](https://www.w3.org/WAI/ARIA/apg/patterns/treegrid/)

## 7. 可选远程查询模式

**场景。** 数据量、权限范围或网络载荷使宿主无法一次返回全部记录，需要由服务端筛选和排序。

**当前证据。** [types.ts:35](../app/src/ntable/types.ts#L35) 接收完整 rows；[tree.ts:16](../app/src/ntable/tree.ts#L16) 在本地递归投影；[NTable.tsx:8](../app/src/ntable/NTable.tsx#L8) 搜索状态在组合组件内。[business-api-contract.md:223](./business-api-contract.md#L223) 明确说明无分页/total 支持。行虚拟化减少 DOM，不消除全量下载与本地计算。

**MVP。** 先支持平铺记录的显式 remote 模式：受控 query/search、已加载 rows、total、加载更多和请求状态，关闭对应本地过滤/排序。宿主拥有请求、缓存、取消和鉴权。树形远程加载另做协议，不能把不完整 children 谎报成完整子树。

**收益与成本。** 解锁大规模接入，但契约、结果计数、加载窗口、选择范围和竞态复杂度高。先采集真实记录量、列数、传输耗时与筛选耗时，再决定启动；本文没有证明现有本地模式已经遇到性能瓶颈。

**边界。** 不内置特定请求库或业务 URL。页脚仍只显示计数；按需加载可沿现有滚动交互延伸。初版远程全选只选已加载且可见行，不宣称选中服务端所有匹配项。

**验收。** 旧查询晚到不覆盖新查询；远程结果不被本地再过滤；计数区分 total 与加载数；重复页不会重复记录；失败重试不会跳过数据；查询变化重置窗口和选择策略一致；本地模式不回归。

## 不建议当前加入的方向

- AI、提醒、分组、行内编辑、字段类型编辑、填色、行高控制：与 [app/AGENTS.md:20](../app/AGENTS.md#L20) 明确范围冲突。
- 看板、日历、甘特、公式、关联记录平台：会显著改变嵌入式表格定位；不能因为其他产品存在就加入。
- 内置审批、权限系统、编辑器、数据库或导出服务：属于宿主业务。若做导出，组件最多提供明确的选择/查询/字段投影，文件生成、完整数据获取和权限校验在宿主。
- 仅扩充“更多字段类型”或再做 AND/OR、冻结列、树形行：前者受当前 schema 规则限制，后者已有，均不是此次最优增量。
